# MedDesk — Полный обзор кода и архитектуры

**Рецензент:** Claude (Fable 5) · **Дата:** 2026-06-10
**Охват:** весь репозиторий — backend (Django 5 / DRF), frontend (React 18 / Vite / TS), Docker/nginx, документация, трассировка реальных сценариев.

---

## 1. Общее резюме

Проект в хорошей форме для своего возраста: чистая структура репозитория, разумное разделение Django-приложений, импортированы реальные исторические данные (470 дней / ~10 тыс. транзакций), деплой работает. Однако есть **два критических бага целостности данных**, **один системный пробел в безопасности** и **одно системное логическое противоречие**, которые нужно исправить прежде, чем клиника начнёт опираться на эту систему в финансовых решениях:

| # | Проблема | Критичность |
|---|---|---|
| C1 | **Finance API не проверяет роли** — любой авторизованный пользователь (врач, регистратор) может читать полный P&L и записывать/перезаписывать кассовые отчёты | 🔴 Критично (безопасность) |
| C2 | **MacDent синхронизация перезаписывает вместо суммирования** — дневная выручка врача = его *последний* платёж за день, а не итого → ФОТ будет систематически занижен | 🔴 Критично (деньги) |
| C3 | **Переоткрытие + сохранение импортированного дня дублирует все транзакции** — строки из Excel пересохраняются как ручные копии → доходы/расходы удваиваются во всех отчётах | 🔴 Критично (деньги) |
| C4 | **Три противоречащих друг другу модели зарплат сосуществуют** — `salary.py` (почасовая, пороговая), фронтенд P&L (% от выручки, прогрессивная, из `SalaryRule`), расчёт ФОТ (% от выручки, прогрессивная, из KPI-полей `StaffMember`). Редактирование ставок в UI не влияет на реальный расчёт ФОТ | 🔴 Критично (логика) |
| C5 | **Цепочка остатков молча ломается при редактировании прошлого дня** — последующие дни сохраняют устаревшие входящие остатки; восстановление — ручная management-команда | 🟠 Высокое |
| C6 | **Удаление сотрудника каскадом удаляет всю историю выручки и ФОТ** | 🟠 Высокое |

Всё остальное (полные списки ниже) поддаётся инкрементальному исправлению.

## 2. Бизнес-цели (как заявлено)

Из `CLAUDE.md`, `docs/meddesk_finance_architecture.md`, `docs/PROGRESS.md`:

1. Заменить ручной процесс `MacDent → xlsx → Excel → ручной подсчёт → выплата врачам` на: автосинхронизацию MacDent → автоматический расчёт ФОТ → подтверждение владельцем → аналитика в реальном времени.
2. Планировщик расписания врачей/анестезиологов с правилами конфликтов (врачи не могут делить кабинет+час; анестезиологи не могут пересекаться между собой, но *могут* — с врачами) и P&L-прогнозом.
3. Ввод кассы за день по 3 счетам (Kaspi pay / Halyk / Наличные) с закрытием/переоткрытием дня и журналом аудита.
4. Ролевой доступ: owner / admin / doctor / anesthesiologist / receptionist — финансовые данные ограничены для owner (admin — частично).
5. Мультиклиника («один пользователь может быть в нескольких клиниках»).
6. Правила разработки: fat models / thin views, бизнес-логика в `services.py`, **расписание не хранить в localStorage**, не смешивать личные финансы с кассой клиники.

Рецензия ниже оценивает код по этим критериям.

## 3. Критические находки (детально)

### C1. Finance API фактически открыт для любого авторизованного пользователя

Каждый finance-endpoint использует только `IsAuthenticated`:

- `api/v1/finance/views.py` — `FinanceSummaryView`, `FinanceDailyView`, `FinanceExpensesView`, `FinanceBalancesView`, `DoctorsRevenueView`, `DailyReportView` (GET **и POST**), `PayrollListView` — никакой проверки кроме аутентификации.
- Проверки роли (`_is_owner`, `_is_owner_or_admin`) есть только для *закрытия/переоткрытия/расчёта ФОТ/подтверждения*.

Система «роль → вкладки» (`RoleTabAccess`) управляет только тем, **какие вкладки рендерит React**. API-слой её никогда не консультирует. Последствия, проверенные по коду:

- **Регистратор или врач могут `GET /api/v1/finance/summary/`** и видеть полный P&L клиники, остатки и выручку каждого врача (`DoctorsRevenueView` даже отдаёт `kpi_threshold` каждого врача).
- Любой авторизованный пользователь может **`POST /api/v1/finance/daily-report/`** и перезаписать кассу за любой открытый день, включая подделку `opening_balances` (сервер доверяет вводимым остаткам — см. C5).
- Любой авторизованный пользователь может **CRUD-ом управлять сотрудниками и их тарифными правилами**: `StaffMemberViewSet` (`api/v1/staff/views.py:9-24`) — только `IsAuthenticated`. Врач может `PATCH` свой `salary_rule.base_rate`.
- Любой авторизованный пользователь может **`PUT /api/v1/scheduler/state/`** и заменить всё расписание *вместе с блоком расходов* (аренда, маркетинг, материалы — финансовые данные хранятся внутри scheduler JSON; см. N3).
- `PayrollListView` (`finance/views.py:611`) позволяет любому пользователю посмотреть суммы ФОТ всех сотрудников.

**Направление исправления:** один DRF-класс разрешений на каждую «вкладку» (или capability роли), основанный на тех же данных `RoleTabAccess`, применённый к каждому view. Матрица вкладок должна быть источником правды для API, а не только для UI.

### C2. MacDent sync: выручка перезаписывается при каждом платеже

`apps/finance/services/sync.py:74-84`:

```python
DoctorRevenue.objects.update_or_create(
    doctor=staff, date=pay_date,
    defaults={"revenue": Decimal(str(p.get("summ", 0))), "patients_count": 1, ...},
)
```

`payment/find` возвращает **отдельные платежи** (список `pays`). При N платежах одного врача за один день каждая итерация *заменяет* `revenue` — сохранённая дневная выручка равна **последнему платежу**, `patients_count` всегда 1, а `raw_data` содержит только последний платёж. Поскольку `calculate_payroll` суммирует `DoctorRevenue`, **ФОТ будет рассчитан от доли реальной выручки** в момент получения боевого токена.

Также:
- Синхронизация молча **перезапишет строки `source="manual"`/`"excel"`** для того же врача+дата.
- `MacDentSync.raw_response` нигде не заполняется.

**Исправление:** агрегировать платежи по (врач, дата) перед upsert-ом; или накапливать через `F('revenue') + amount` внутри транзакции, привязанной к run синхронизации.

### C3. Редактирование переоткрытого импортированного дня дублирует все транзакции

Трассировка (проверена построчно):

1. `GET daily-report` (`finance/views.py:367-380`) возвращает **все** транзакции — `source` в payload *не включён*.
2. `DailyInputTab.loadReport` (frontend, ~строка 659) загружает каждую транзакцию в редактируемые строки.
3. `buildPayload` (~строка 746) отправляет все непустые строки обратно.
4. `DailyReportView.post` (`finance/views.py:480`) удаляет **только строки `source="manual"`**, затем пересоздаёт *всё из payload* как `source="manual"`.

→ Для любого из 470 импортированных дней, который владелец переоткроет и пересохранит, **каждая excel-транзакция теперь существует дважды** (раз как `excel`, раз как `manual`). Месячный доход/расход за этот день удваивается в `FinanceSummaryView`, а пересчитанный `balance_end` (только из payload) больше не совпадает с таблицей транзакций.

**Исправление:** включить `source` в GET-payload; трактовать не-manual строки как read-only на клиенте; при POST либо заменять *все* строки, либо сверять по id.

### C4. Три модели зарплат, не согласующиеся между собой

| Где | Входные данные | Семантика |
|---|---|---|
| `apps/staff/salary.py` (+ pytest) | `SalaryRule.base_rate/elevated_rate` | **почасовая ставка × часы**; повышенная ставка применяется ко *всем* часам как только выручка ≥ порога (cliff) |
| Frontend `ClinicScheduler.calcDoctorSalary` (строка 58) | те же поля `SalaryRule`, но трактуются как **дроби** (`0.30`) | % от выручки, **прогрессивный** выше `threshold2` |
| `FinanceSyncService.calculate_payroll` + `PayrollCalculation` | `StaffMember.kpi_threshold / rate_below_kpi / rate_above_kpi` (проценты, `30.00`) | % от выручки, прогрессивный |

Порождаемые проблемы:

- `salary.py` — **мёртвый код**: ничто его не вызывает, но он единственный покрыт тестами (`test_salary.py` проверяет *почасовую* семантику). Тесты сертифицируют поведение, которого в продукте нет.
- UI сотрудников редактирует `SalaryRule`, но **реальный расчёт ФОТ читает KPI-поля `StaffMember`, которых нет в `StaffMemberSerializer`** (`api/v1/staff/serializers.py` — `kpi_threshold`, `rate_below_kpi`, `rate_above_kpi` отсутствуют в `fields`). Владелец буквально не может настроить ставки ФОТ через приложение — только через Django admin.
- Прогноз во вкладке P&L и модуль расчёта ФОТ по конструкции дадут разные числа для одного и того же врача.

**Исправление:** выбрать одну модель (KPI-прогрессивная соответствует архитектурному документу), удалить `SalaryRule` + `salary.py` (или мигрировать данные), раскрыть KPI-поля в сериализаторе (с записью только для owner), сделать так чтобы и прогноз P&L, и расчёт ФОТ обращались к одному backend-сервису.

### C5. Входящие остатки берутся от клиента и цепочка не распространяется

- `DailyReportView.post` (`finance/views.py:497-514`) принимает `opening_balances` **из тела запроса** и сохраняет как `balance_start`. Любой клиент (и любая роль — см. C1) может задать произвольные остатки.
- При редактировании прошлого дня `balance_end` меняется, но **ни один из последующих дней не пересчитывается**. Бридж на стороне GET (`_build_report_response:393-405`) применяется только к дням *без* отчёта. Дни с уже созданными отчётами хранят устаревший `balance_start` навсегда.
- В репозитории есть management-команды `propagate_balances`, `recalculate_balances`, `fix_opening_balances`, `check_balance_chain` — то есть дрейф цепочки известен и исправляется *вручную*. Для кассовой книги это бомба замедленного действия.

**Исправление:** делать `balance_start` серверно-производным (от `balance_end` предыдущего дня), пересчитывать вперёд (или помечать следующие дни как устаревшие) при любом сохранении, прекратить принимать остатки от клиента кроме самого первого дня.

### C6. Жёсткое удаление сотрудника уничтожает финансовую историю

`StaffMemberViewSet` — это `ModelViewSet` → `DELETE /staff/{id}/` выполняет реальное удаление. `DoctorRevenue.doctor` и `PayrollCalculation.staff_member` имеют `on_delete=CASCADE`. Удаление уволенного врача из списка **стирает его строки выручки и подтверждённые записи ФОТ**, ретроспективно меняя историческую аналитику.

Также: `get_queryset` фильтрует `is_active=True`, поэтому деактивированный сотрудник не может быть реактивирован через API (PATCH возвращает 404), а модель имеет поле `is_active` именно для того чтобы избежать удаления — viewset противоречит собственной модели.

**Исправление:** переопределить `destroy` как мягкое удаление (`is_active=False`); `on_delete=PROTECT` для FK выручки/ФОТ.

## 4. Прочие баги

### Backend

1. **`EmailLoginView` возвращает 500 при дублирующихся email** (`api/v1/auth/views.py:29`): `User.email` не уникален в модели, `User.objects.get(email__iexact=...)` бросает `MultipleObjectsReturned` → необработанная 500. Добавить уникальное ограничение на email (без учёта регистра) и/или `.filter(...).first()`.
2. **Sync сообщает "success" при ошибке MacDent** — `MacDentClient._post` поглощает все ошибки и возвращает `{}` (`services/macdent.py:18-34`); `_post_all_pages` затем возвращает `[]`/частичный результат; `sync_period` помечает run как `success` с 0/частичными записями. Частичная ошибка страницы (`break` на строке 63) молча обрезает данные посреди синхронизации. Нужно различать «нет данных» и «запрос не удался».
3. **`HourSlot.clean` противоречит заявленному бизнес-правилу** (`apps/schedule/models.py:104-113`): запрос на конфликт врача считает *любой* HourSlot в том же кабинете+час — включая анестезиолога — как конфликт, тогда как правило гласит, что врачи и анестезиологи могут пересекаться. Проверка анестезиолога также игнорирует границы клиники. (Сейчас мёртвый код — см. N1 — но всё равно неверный.)
4. **Инвалидация кэша `RoleTabAccess` — на процесс** (`apps/accounts/apps.py` + `lru_cache` в `permissions.py`): сигнал `post_save` очищает кэш только в том воркере, который обработал PUT. Сейчас gunicorn запускает 1 воркер, поэтому это скрытый риск; как только добавите `-w 4`, изменения прав доступа перестанут применяться к другим воркерам до перезапуска. Используйте нормальный кэш-бэкенд или просто уберите кэш (он экономит один крошечный запрос).
5. **`FinanceSummaryView` — закрывающие остатки месяца** (`views.py:120-135`): берёт остатки из буквально последнего `DailyReport` месяца; если у этого отчёта нет строк остатков (возможно для вручную созданных отчётов до добавления кода остатков), весь месяц показывает `null` даже если предыдущие дни имеют остатки.
6. **Категоризация расходов** (`views.py:63-69`): захардкоженные `Q`-фильтры по ключевым словам прямо во view, включая личные имена («мурзаб», «калымбет»). При этом модель `TransactionCategory` (с JSON-полем `keywords`, спроектированная именно для этого) **нигде и никогда не используется**. `icontains="зп"` также совпадает с любым словом, содержащим «зп». Бизнес-логика во view нарушает собственное правило проекта о fat-models.
7. **`_is_owner` не привязан к клинике** (`views.py:419-436`): статус владельца *любой* клиники даёт права владельца везде. Аналогично для `_is_owner_or_admin` и `get_user_auth_context` (берёт `.first()` членства произвольно). С одной клиникой работает; это ловушка для цели #5.
8. **Анестезиологи никогда не получают расчёт ФОТ**: `calculate_payroll` итерирует только по `DoctorRevenue` — сотрудники без записей выручки (анестезиологи по определению) не получают `PayrollCalculation` вообще. Архитектурный документ говорит что ФОТ для сотрудников, а не только врачей.
9. **`import_excel` игнорирует задокументированные в Excel закрывающие остатки** по kaspi/halyk/cash (вычисляет свой `end`) и никогда не предупреждает когда вычисленный ≠ заявленному — бесплатная проверка согласованности выброшена. Доход+расход в одной строке делят один комментарий (незначительно).
10. **Нет троттлинга при входе** — `EmailLoginView` не имеет rate limit; в сочетании с HTTP-only деплоем (ниже) учётные данные поддаются брутфорсу.
11. **Ротация refresh-токенов без blacklist**: `ROTATE_REFRESH_TOKENS=True`, но `rest_framework_simplejwt.token_blacklist` не установлен — старые refresh-токены остаются валидными до истечения срока, поэтому ротация ничего не даёт.
12. **Celery настроен, но пуст**: существует только `sync_macdent_today`; запланированная задача `calculate_monthly_payroll` отсутствует. Beat использует `DatabaseScheduler` без заполненных периодических задач — ничего не запускается пока кто-то не создаст записи вручную в admin (в документации этот шаг не упомянут).

### Frontend

13. **Offline-очередь / rollback используют устаревшие замыкания** (`DailyInputTab.tsx` ~638-785): эффект переподключения намеренно опускает зависимости, а rollback в `doSave` захватывает `prevRows` в момент создания callback — правки, сделанные оффлайн или во время медленного сохранения, могут молча теряться/откатываться.
14. **Перезапись вычета в `calcDoctorSalary`** (`ClinicScheduler.tsx:58-64`): при обоих установленных флагах `deductLab` *заменяет* вычет implant вместо суммирования — `base = revenue*(1-IMPLANT_RATE)` отбрасывается следующей строкой.
15. **Формула дневной выручки во вкладке Week неверна** (`ClinicScheduler.tsx:921`): `dayRevenue = Σhours × 4.3/7 × 33000`. Дневная выручка должна быть часами этого дня × ставка; умножение часов одного дня на 4.3/7 даёт число без смысла.
16. **Константы P&L захардкожены**: `REVENUE_PER_HOUR=33000` едина для всех врачей, налог 3%, банковская комиссия 2%, 4.3 недели/месяц, breakeven `fixed/0.55` (предполагает фиксированную долю переменных расходов 45% независимо от настроенных ставок). Нормально для наброска, но вводит в заблуждение как «модуль P&L».
17. **`@ts-nocheck` на `ClinicScheduler.tsx` из 1085 строк** — крупнейший, насыщенный логикой компонент с отключённым TypeScript.
18. **Молчаливая ошибка `fetchClosedDates`** — при ошибке иконки замков исчезают и день выглядит редактируемым (сервер всё равно отклонит, но UX врёт).
19. **JWT в `localStorage`** (`api/client.ts`) — уязвимо к XSS; приемлемый компромисс только при добавлении CSP и (критически важно) HTTPS.
20. **Права доступа не обновляются при обновлении токена** — `tabs` из `/auth/me/` сохраняются до перезагрузки, даже если владелец отозвал доступ.
21. **`fetchStaff` читает только первую страницу** — DRF `PAGE_SIZE=100`; сотрудник #101 молча исчезает из планировщика. Скрытый риск, но однострочное исправление сейчас лучше, чем загадка позже.

## 5. Нелогичные части (противоречия, мёртвый код)

- **N1. Два параллельных расписания.** Реляционные модели `Room / WeekTemplate / DaySlot / HourSlot` — со своей логикой валидации и миграциями — **полностью не используются**. Реальный планировщик сохраняет один JSON-блоб (`SchedulerState`), серверная валидация которого сводится к «people — это список словарей» (`SchedulerStateSerializer`). Все правила конфликтов живут на клиенте, что противоречит правилу проекта «не писать бизнес-логику в views / не хранить расписание в localStorage» по духу: сервер сохраняет что угодно, что пришлёт любой клиент.
- **N2. Тесты сертифицируют мёртвый код.** Единственные значимые тесты бизнес-логики (`test_salary.py`) тестируют `salary.py`, который ничто не вызывает (см. C4). `finance/calculator.py` — обязательный по CLAUDE.md к тестированию — не существует. Расчёт ФОТ, синхронизация, импорт и все API-разрешения не имеют ни одного теста.
- **N3. Финансовые данные внутри scheduler-блоба.** `expenses` (аренда, маркетинг, материалы, % наркоза) живут в `SchedulerState.data`, доступны на чтение/запись всем с вкладкой расписания — что противоречит «финансы только owner/admin» и дублирует домен модуля финансов.
- **N4. `TransactionCategory` и `DailyTransaction.category`** существуют, зарегистрированы в admin и **нигде никогда не читаются и не записываются** ни одним кодовым путём (категоризация захардкожена во view, см. баг 6).
- **N5. CLAUDE.md описывает систему, отличающуюся от кода**: модели `MonthlyExpenses`/`RevenueRecord` и endpoints (`/finance/expenses/{month}` PATCH, `/schedule/week/`, `/rooms/`) не существуют; задокументированная Docker-конфигурация отличается от реальной. Новые участники (или будущие сессии Claude) будут введены в заблуждение. Аналогично со списком API (маршрут `/rooms/` отсутствует; `DELETE /schedule/slot/` не существует).
- **N6. `WeekTemplate.week_number` + (year, month)** не имеет ограничения уникальности и не привязан к реальным датам — даже если реляционное расписание будет возрождено, модель не может корректно представить «клонировать по месяцам».
- **N7. `DailyReport.date` глобально `unique=True`** — одна кассовая книга для всей системы. Нормально сейчас, но на уровне схемы жёстко блокирует цель #5 (мультиклиника), тогда как другие модели (`StaffMember`, `Room`) добросовестно несут FK на `clinic`. Кодовая база не может определиться — она мультитенантная или нет.

| Цель | Вердикт |

Реляционный дизайн вернётся когда действительно понадобится посуточное планирование (вместо недельного шаблона).
6. **Использовать `TransactionCategory`.** Вынести категоризацию по ключевым словам в сервис, засидить категории (с личными именами как *данными*, не кодом), сохранять `DailyTransaction.category` при сохранении, группировать по ним на дашборде. Затем разделить операционные vs займы/капзатраты/внутренние в KPI прибыли.

## 8. Трассировка реальных сценариев

Каждый сценарий прослежен по реальным кодовым путям.

### S1. «Регистратор вводит кассу дня, владелец закрывает день» ✅/⚠️
Регистратор открывает «Ввод дня», вводит транзакции, сохраняет → `POST daily-report` делает upsert, остатки рассчитываются. Владелец нажимает 🔒 → `close/` проверяет `_is_owner` → OK. Закрытый день отклоняет дальнейшие сохранения (400) и UI показывает только для чтения. **Работает.** Оговорки: если `fetchClosedDates` молча падает, иконка замка исчезает (баг 18); проверка закрытия — для owner любой клиники (баг 7); и регистратор мог бы так же переписать *даты прошлого месяца* (C1) — дата ничем не ограничена.

### S2. «Два регистратора вводят один и тот же день параллельно» ❌
Оба загружают день, оба добавляют строки, оба сохраняют. Сохранение #2 удаляет все manual-строки и пишет свой снапшот → **записи регистратора #1 исчезают без предупреждения**. Нет проверки версии, нет слияния. Аналогичная гонка last-write-wins при редактировании планировщика (PUT всего блоба).

### S3. «Владелец исправляет ошибку прошлого вторника» ❌
Владелец переоткрывает день, исправляет одну сумму, сохраняет. (а) Если день был импортирован из Excel — **каждая транзакция дублируется** (C3) — при 470 импортированных днях это *произойдёт*. (б) `balance_end` вторника меняется, но среда-сегодня сохраняют старые входящие остатки (C5) — «Остаток» на дашборде больше не соответствует реальности, пока кто-нибудь не зайдёт по SSH и не запустит `propagate_balances`. Кассовая книга расходится с реальными деньгами в кассе.

### S4. «Боевой токен MacDent получен, почасовая синхронизация запущена» ❌
`sync_macdent_today` запускается (если кто-то не забыл создать расписание Beat в admin — баг 12). Д-р Дана принимает 6 пациентов, 6 платежей по 50 тыс. → `DoctorRevenue.revenue = 50 000`, а не 300 000 (C2). В конце месяца `calculate_payroll` выплачивает ей ~30% × (шестой части её выручки). Врач замечает; доверие к системе умирает в первый же день. Дополнительно: любой платёж, чей `doctor` id не совпадает ни с каким `macdent_id`, молча пропускается с только серверным лог-предупреждением — и по данным `PROGRESS.md`, `macdent_id` ещё не заполнен для реальных врачей.

### S5. «Врач заходит из дома» ⚠️
Вход по email работает (при условии уникальных email — баг 1). Врач видит только вкладки расписания. Но с тем же JWT в DevTools можно сделать `GET /api/v1/finance/payroll/?month=2026-05` и прочитать **зарплаты коллег**, или `PATCH /api/v1/staff/{their_id}/` и повысить свою `salary_rule.base_rate` (C1). По plain HTTP на публичном IP кто угодно на пути также может перехватить токен (рек. 8).

### S6. «Владелец смотрит итоги мая: выручка по врачам, P&L, ФОТ» ⚠️
DoctorsTab и дашборд нормально рендерятся из импортированных данных. Но: «Прибыль» включает займы/капзатраты (§6); выручка по врачам покрывает только врачей с `DoctorRevenue` (excel/ручной импорт секции врачей — команда импорта фактически *останавливается* на маркере секции врачей и никогда не загружает её, так что выручка по врачам существует только там, где введена другими способами); вкладка P&L в планировщике показывает прогнозы на основе захардкоженных 33 000 тг/час, которые не согласуются с реальными финансовыми данными. Три экрана — три версии правды (C4, баг 16).

### S7. «Клиника открывает второй филиал» ❌
Ограничение уникальности `DailyReport.date` сразу даёт коллизию; `get_default_clinic()` захардкоживает одну клинику для планировщика; `_is_owner` не может различить филиалы (N7, баг 7). Требует архитектурного решения из рек. 4 прежде всего.
